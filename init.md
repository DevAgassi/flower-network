# Project Context & Architecture Specification: Omnichannel Flower Network

## 1. Мета проєкту та бізнес-модель
Це пет-проєкт / R&D-платформа для глибокого вивчення побудови високонавантаженого e-commerce, здатного масштабуватися від локальної мережі до великої системи (рівня Rozetka / аптечних мереж) без переписування кодової бази.

* **Домен:** Мережа квіткових магазинів одного власника в межах міста (5–9 роздрібних точок + 1–2 центральні склади).
* **Модель роботи (Omnichannel / BOPIS — Buy Online, Pick Up In Store):**
  * Клієнт на сайті бачить наявність товару в конкретних магазинах міста (за принципом аптечної довідки).
  * Можливість оформити самовивіз із конкретної точки або доставку кур'єром.
  * Синхронізація офлайн-продажів (POS-екран флориста на касі в магазині) та онлайн-замовлень у реальному часі.
  * Внутрішні переміщення товару між магазинами та центральним складом (Stock Transfers).
  * Облік списань (унікальна специфіка квітів — псування товару).
  * Букети як комплекти: збираються з окремих квітів, які списуються зі складу.
* **Архітектурний приціл на майбутнє:** База даних та модулі проєктуються так, щоб у майбутньому систему можна було безболісно розширити до повноцінного multi-vendor маркетплейсу (додаванням сутності `merchants`).

> Карта модулів, фіч і етапів з діаграмами — у [ROADMAP.md](ROADMAP.md).

## 2. Ключові архітектурні рішення (Висновки дослідження)
1. **Відмова від готових CMS та Headless-коробок (OpenCart, Directus, Vendure):**
   * Готові CMS накладають обмеження на складну бізнес-логіку (матриці SKU, транзакційне резервування залишків, кастомна аналітика, POS-інтерфейс).
   * На старті вони економлять час, але через 1–2 роки розвитку призводять до дорогого рефакторингу та костилів.
2. **Архітектурний патерн: Модульний моноліт (Modular Monolith) + API-First:**
   * Бекенд пишеться як єдиний проєкт, але жорстко розділений на ізольовані бізнес-модулі.
   * Модулям заборонено робити прямі SQL-запити до чужих таблиць — взаємодія відбувається лише через публічні сервіси або внутрішні події (Event-Driven).
   * Це дозволяє при зростанні навантаження винести будь-який модуль (наприклад, `Inventory` або `Orders`) в окремий мікросервіс без переписування логіки.
   * **Єдиний виняток з правила ізоляції — модуль `analytics`:** йому дозволено читати чужі таблиці *лише* через Materialized Views (read-only). Виняток задокументований свідомо, щоб не будувати окремий конвеєр даних на старті.
3. **Stateless-інфраструктура з першого дня:**
   * Жодних локальних файлів на сервері (медіа зберігаються в S3-сумісному сховищі).
   * Сесії та черги фонових задач живуть у Redis.
   * Кошик — окремий модуль зі сховищем у PostgreSQL за інтерфейсом `CartRepository` (див. ADR-9 у розділі 9). Stateless-принцип це не порушує: стан не зберігається ні в пам'яті процесу, ні у файлах сервера.
4. **Надійна доставка подій (Transactional Outbox):**
   * `@nestjs/event-emitter` працює в пам'яті процесу: при падінні після коміту подія губиться. Тому кожна доменна подія записується в outbox **в тій самій транзакції**, що й бізнес-зміна (`outbox.add(tx, …)`).
   * Реалізація — офіційний пакет `@nestjs/outbox` (ADR-12): таблиці в окремій схемі `nest_outbox` (`messages`, `inbox`, `dead_letters`), relay з орендою повідомлень (lease), повторами та dead-letter, процес `worker` (`apps/api/src/worker.ts`).
   * Кожен споживач ідемпотентний: inbox споживача (`consumer` + id повідомлення) відкидає повторну доставку; запис у ту саму БД — через `ctx.processInTransaction(tx, …)` (рівно один раз).
   * Саме це робить можливим подальше винесення модуля в мікросервіс (outbox → брокер повідомлень) без зміни бізнес-коду.
5. **Джерело істини для залишків — журнал `stock_movements`:**
   * `location_stocks.physical_qty` — похідний кеш, який оновлюється в тій самій транзакції, що й запис руху.
   * Нічний воркер звіряє `location_stocks` із сумою рухів і сигналізує про розбіжності.

## 3. Технологічний стек
* **Frontend (Вітрина + Адмін-панель `/admin` + POS-каса флориста `/pos`):**
  * **TanStack Start** (Vite + Nitro + TanStack Router + TanStack Query).
  * Сувора типізація URL search-параметрів для фільтрів каталогу та наявності по магазинах.
  * UI: Tailwind CSS + Shadcn UI + TanStack Table.
  * SSR для публічних сторінок каталогу (SEO): ЧПУ-slug-и, `sitemap.xml`, мета-теги.
* **Backend:**
  * **NestJS** (TypeScript) — модульний моноліт.
  * Події між модулями: **`@nestjs/outbox`** (transactional outbox, ADR-12); фоновий процес `worker` (той самий код, без HTTP) публікує повідомлення і виконує задачі за розкладом (`@nestjs/schedule`).
  * Відкладені задачі: **BullMQ** (на базі Redis) — зняття прострочених резервів, оновлення аналітики, звірка залишків; додається з першою фічею, якій він потрібен.
  * Real-time сповіщення (нові онлайн-замовлення для флористів на точках): **WebSockets / SSE**.
  * ORM / query builder: **Drizzle ORM** + drizzle-kit для міграцій (ADR-1).
  * Менеджер процесів (PM2) не використовується: перезапуск і масштабування робить Docker / оркестратор (один процес на контейнер).
* **Монорепозиторій (ADR-10):** pnpm 12 workspaces + Turborepo 2. Застосунки — `apps/api` (NestJS 12, ESM), `apps/web` (TanStack Start); спільний код — `packages/*` (`@flower/shared`, `@flower/typescript-config`). Структура описана в [docs/modules/platform/monorepo.md](docs/modules/platform/monorepo.md).
* **Конфігурація та режими:** `NODE_ENV` (`development` / `test` / `production`); змінні середовища валідуються zod-схемою при старті (api — `@nestjs/config` + zod, web — zod у Nitro-плагіні). Development читає `.env`, production — лише реальні змінні (12-factor). `pnpm dev` — режим розробки, `pnpm start` — зібрані застосунки в production-режимі.
* **Контракт API:**
  * Запити й відповіді описуються zod-схемами (NestJS 12 Standard Schema: `@Body({ schema })`, глобальний `StandardSchemaValidationPipe`); OpenAPI-схема генерується з NestJS (`@nestjs/swagger` 12) у закомічений `apps/api/openapi.json` (`pnpm api:generate`).
  * Типізований клієнт для фронтенду генерується зі схеми (`openapi-typescript` + `openapi-fetch`) і лежить у пакеті `@flower/api-client`.
* **Бази даних та інфраструктура (Docker Compose):**
  * **PostgreSQL 17** — основна реляційна БД.
  * **Redis** — кеш каталогу, сесії, брокер для BullMQ.
  * **RustFS** — локальне S3-сумісне сховище для фото товарів та букетів (замість MinIO, ADR-11). Застосунок працює зі стандартним S3 API, тож у продакшені це може бути будь-який S3-провайдер.
  * **pgAdmin** — веб-інтерфейс до PostgreSQL для локальної розробки (без логіна, сервер підключено автоматично).
  * Локальна інфраструктура описана в `compose.yaml` (запуск: `pnpm infra:up`).
  * **Meilisearch** *(опціонально на етапі масштабування)* — швидкий фасетний пошук.
* **Спостережуваність:**
  * Структуровані JSON-логи (`pino`) з `request_id` / `trace_id`.
  * **OpenTelemetry** для трейсингу, **Prometheus + Grafana** для метрик (у `docker-compose`).
* **Якість та доставка:**
  * Лінтер: **oxlint** (у `apps/api` — з перевіркою типів). Тести: **Vitest**. Форматування: **Prettier** (корінь репозиторію).
  * CI: GitHub Actions (lint, typecheck, unit/integration-тести, перевірка міграцій).
  * Навантажувальні тести: **k6**.
  * Бекапи PostgreSQL (`pg_dump` / WAL-архівація) — на етапі розгортання.

## 4. Еталон проєктування БД: Підхід Spree Commerce
За основу реляційної моделі даних береться архітектура **Spree Commerce** (визнаний індустріальний стандарт для складного e-commerce), адаптована під мережу точок.

### 4.1. Загальні правила
* **Гроші** зберігаються в копійках як `bigint` (валюта — UAH). Жодних `float`.
* **Час** зберігається як `timestamptz` в UTC. «Бізнес-день» для звітів, графіків роботи точок і слотів доставки рахується в часовому поясі **Europe/Kyiv**.
* **М'яке видалення** (`deleted_at`) для сутностей каталогу та складу (`products`, `product_variants`, `location_stocks`, `taxons`): видалений товар не ламає старі замовлення й журнал рухів.
* **Людиночитні номери документів** (`number`), окремі від `id`: замовлення `R…`, відвантаження `H…`, оплати `P…`, повернення `RA…`. Внутрішній `id` назовні не показується.
* **Метадані для інтеграцій:** `public_metadata` та `private_metadata` (`jsonb`) у ключових таблицях (`products`, `product_variants`, `orders`, `shipments`, `payments`, `users`) — дані інтеграцій без нових міграцій.
* **Історія станів (`state_changes`):** `entity_type` (`order` / `payment` / `shipment` / `return`), `entity_id`, `previous_state`, `next_state`, `user_id`, `created_at`. Кожна зміна стану пишеться сюди в тій самій транзакції.
* **Посилання на документ-джерело** робляться через `source_type` + `source_id` з перевіркою в коді або через окремі nullable-колонки з FK. Polymorphic-зв'язки «на будь-яку таблицю» без перевірки (як `originator` у Spree) заборонені.

### 4.2. Каталог
1. **Розділення `products` та `product_variants` (SKU):**
   * Кожен товар (`products`) має щонайменше один майстер-варіант (`is_master = true`) або набір варіацій (наприклад, Троянда Еквадор: 50см, 60см, 80см; Букет: S, M, L).
   * Уся логіка кошика, замовлень, цін та складських залишків працює **виключно з `product_variants` (SKU)**, ніколи з батьківським `product`.
2. **Дерева категорій (`taxonomies`, `taxons`, `product_taxons`):**
   * `taxonomies` — незалежні дерева, наприклад «Категорія» та «Привід» (день народження, весілля). Товар може бути в кількох деревах одночасно.
   * `taxons` реалізуються через **Materialized Path на типі `ltree`** з GiST-індексом: вибірка товарів з усіх підкатегорій одним запитом без рекурсії (`path <@ 'flowers.roses'`). Nested Sets (`lft`/`rgt`, як у Spree) не використовуються: дерево мале й рідко змінюється, а `ltree` простіший у підтримці.
   * `product_taxons` містить `position` для ручного сортування товарів у категорії.
3. **Ціни (`prices`):** `variant_id`, `amount` (копійки), `currency`.
4. **Комплекти / букети (`variant_components`):**
   * `kit_variant_id`, `component_variant_id`, `qty` — склад букета (з яких SKU і скільки штук).
   * Поле `product_variants.kit_type`:
     * `none` — звичайний товар;
     * `stocked` — букет збирається заздалегідь і має власний залишок (збірка — окрема операція, див. 4.3);
     * `made_to_order` — букет збирається під замовлення; доступність обчислюється як `min(floor(available(component) / qty))` по всіх компонентах на точці.
   * **Довільний букет на касі** (флорист збирає з наявного): рядок замовлення зберігає фактичний список використаних компонентів, які списуються зі складу.

### 4.3. Склад
1. **Мульти-складський облік (`locations` та `location_stocks`):**
   * `locations` — довідник усіх фізичних точок (магазини з координатами та графіком роботи + центральні склади).
   * `location_stocks` — зв'язок `location_id` + `variant_id`. Містить:
     * `physical_qty` (фізичний залишок на точці),
     * `reserved_qty` (заброньовано активними замовленнями),
     * Доступний для продажу залишок обчислюється як `physical_qty - reserved_qty`.
2. **Журнал руху товару (`stock_movements` — Ledger-підхід):**
   * Заборонено просто перезаписувати цифру залишку без запису причини. Кожна зміна **фізичного** залишку фіксується в таблиці рухів.
   * Типи рухів: `receipt`, `sale_online`, `sale_pos`, `return`, `write_off`, `transfer_out`, `transfer_in`, `transfer_loss`, `assembly_consume`, `assembly_produce`, `count_adjustment`.
   * Кожен рух має посилання на документ-джерело (`source_type` + `source_id`): `goods_receipt`, `order`, `stock_transfer`, `stock_count`, `return`, `write_off`, `assembly`. Від будь-якого руху можна перейти до документа, що його створив.
   * Резерви не змінюють фізичний залишок, тому живуть у `stock_reservations` (з власною історією станів), а не в журналі рухів.
3. **Партії (`stock_batches`):**
   * `location_id`, `variant_id`, `received_at`, `qty_remaining`, `unit_cost`, `receipt_id`.
   * Списання та продажі зменшують партії за принципом **FIFO** (спершу старіші квіти).
   * Рух `write_off` посилається на партію → аналітика «вік квітів на момент списання» та вартість втрат у гривнях.
4. **Збірка букетів (`assembly`):** одна транзакція створює рухи `assembly_consume` (по кожному компоненту) та `assembly_produce` (готовий букет `stocked`).
5. **Переміщення (`stock_transfers`, `stock_transfer_items`):**
   * Статуси: `draft` → `shipped` → `received` → `closed`.
   * `shipped` → рух `transfer_out` на точці-відправнику; `received` → рух `transfer_in` на точці-отримувачі.
   * Товар у дорозі = відвантажене, але ще не отримане; не рахується в доступному залишку жодної точки.
   * Розбіжність `qty_sent - qty_received` фіксується рухом `transfer_loss`.
6. **Інвентаризація (`stock_counts`, `stock_count_items`):**
   * `expected_qty` (з системи) vs `counted_qty` (факт) → рух `count_adjustment` з причиною.

### 4.4. Закупівлі
* `suppliers` — постачальники.
* `goods_receipts`, `goods_receipt_items` — документ приходу: постачальник, точка, SKU, кількість, **закупівельна ціна**. Проведення приходу створює рух `receipt` та партію в `stock_batches`.

### 4.5. Кошик, ціноутворення та замовлення
1. **Кошик — окрема сутність, не замовлення** (на відміну від Spree, де кошик — це `orders.state = cart`; обґрунтування — ADR-9):
   * Таблиці модуля `cart`: `carts` (`token`, `user_id` nullable, `location_id` обраної точки, `expires_at`, `updated_at`), `cart_items` (`variant_id`, `qty`).
   * Доступ — лише через `CartRepository`; реалізація на Redis може бути підставлена пізніше без змін в інших модулях.
   * Фоновий воркер видаляє кошики з `expires_at` у минулому.
   * При оформленні ціни та наявність перевіряються заново; кошик → замовлення → резерв виконуються **в одній транзакції**.
2. **Спільний розрахунок ціни (модуль `pricing`):**
   * `PriceCalculator` — єдине місце розрахунку сум рядків, коригувань (промокоди, доставка) та підсумків. Його викликають і `cart` (показ суми), і `orders` (фіксація суми) — суми в кошику й замовленні не можуть розійтися.
   * Промокоди: `promotions`, `promotion_rules` (умови), `promotion_actions` (що дає знижка), `coupon_codes`.
3. **Машина станів замовлення (за Spree — три незалежні стани):**
   * `orders.state`: `placed` → `confirmed` → `assembling` → `ready_for_pickup` / `in_delivery` → `completed`; також `cancelled`, `pickup_expired`.
   * `orders.payment_state`: `pending` → `paid` / `failed` → `refunded` / `partially_refunded`.
   * `orders.shipment_state`: стан відвантаження (див. 4.7).
   * **Онлайн-оплата:** `placed` переходить у `confirmed` лише після `payment_state = paid`.
   * **Оплата при отриманні:** `placed` → `confirmed` одразу; оплата фіксується на POS у момент видачі.
   * Кожен перехід записується в `state_changes` (див. 4.1). Змінювати стани можна лише через сервіс машини станів, не прямим `UPDATE`.
4. **Ідентифікація замовлення:** `number` (`R…`) для клієнта й персоналу; `token` — безпечне посилання, за яким гість бачить статус замовлення без входу в акаунт.
5. **Підсумки в замовленні (денормалізовані, як у Spree):**
   * `item_total`, `adjustment_total`, `promo_total`, `shipment_total`, `total`, `payment_total`.
   * Перераховуються **лише** сервісом `OrderUpdater` модуля `orders` (через `PriceCalculator`). `payment_total < total` означає недоплату.
6. **Snapshot-історія (`order_items`, `order_adjustments`):**
   * У `order_items` зберігається знімок (snapshot) назви, артикулу, ціни **та собівартості** на момент покупки, щоб зміна цін у каталозі не ламала історію старих замовлень, а маржа рахувалась коректно.
   * Усі знижки, промокоди та вартість доставки виносяться в окрему таблицю `order_adjustments` (як у Spree) для прозорої фінансової аналітики.
   * Кожне коригування прив'язане до рівня (`order_id` обов'язковий + nullable `order_item_id` або `shipment_id`) і має джерело (`source_type`: `promotion` / `shipping` / `manual`, `source_id`) та `label`. Так видно, яка акція дала знижку на який рядок.
7. **Транзакційне резервування (`stock_reservations`):**
   * При оформленні замовлення відбувається блокування рядка в `location_stocks` (`SELECT ... FOR UPDATE`), збільшується `reserved_qty` і створюється запис резерву.
   * **Термін резерву залежить від способу оплати:**
     * онлайн-оплата — 15 хвилин; якщо оплата не пройшла, воркер BullMQ скасовує резерв;
     * оплата при отриманні — до кінця вікна самовивозу (налаштовується); після нього замовлення переходить у `pickup_expired`, резерв знімається.
   * При видачі / завершенні замовлення: `reserved_qty` і `physical_qty` зменшуються в одній транзакції + рух `sale_online`.
8. **Продажі на POS** проходять через той самий модуль `orders` (канал `pos`) — єдиний облік виручки для `pos_sales_count` / `online_sales_count`.
9. **Повернення (за Spree — три окремі кроки):**
   * `return_authorizations` (`number`, `order_id`, `reason_id`, `state`) — клієнт хоче повернути;
   * `return_items` (`order_item_id`, `qty`, рішення: `restock` → рух `return` / `write_off` → рух `write_off`; для квітів типовий випадок — списання) — що саме і що з ним робимо;
   * `refunds` (див. 4.6) — гроші повернено;
   * довідники `return_reasons`, `refund_reasons`.

### 4.6. Оплати
* `payments`: `order_id`, `method` (`online_card`, `pos_cash`, `pos_card`), `provider`, `amount`, `state`, `provider_ref`.
* `payment_events`: сирі webhook-и провайдера; обробка ідемпотентна за `provider_ref` / ключем ідемпотентності.
* `refunds`: повернення коштів, пов'язані з `payments`.
* Провайдер підключається через інтерфейс `PaymentProvider` (конкретний провайдер — ADR-4).

### 4.7. Відвантаження та доставка (`shipments`)
* `shipments`: `order_id`, `location_id` (точка, яка збирає замовлення), `method` (`pickup` / `courier`), `slot_start`, `slot_end`, `state`.
* **Отримувач:** `recipient_name`, `recipient_phone`, `card_message`, `is_anonymous` — отримувач часто не той, хто платить.
* `delivery_zones`: зона доставки, вартість, мінімальна сума замовлення (спосіб задання зони — ADR-8).
* `shipping_rates`: `shipment_id`, `method`, `cost`, `is_selected` — варіанти вартості, розраховані при оформленні; обраний фіксується і не змінюється разом із тарифами.
* `delivery_slots`: доступні часові вікна доставки по точках із лімітом кількості замовлень.
* У v1 одне замовлення = одна точка відвантаження (ADR-2).

### 4.8. Користувачі та доступ
* `users`, `roles` (`owner`, `admin`, `florist`, `courier`, `customer`), `staff_locations` (флорист / кур'єр прив'язаний до своїх точок).
* Клієнт може оформити замовлення без реєстрації (за телефоном); акаунт — опціонально (ADR-3).

### 4.9. POS та фіскалізація
* `cash_shifts`: `location_id`, `user_id`, `opened_at`, `closed_at`, `opening_cash`, `expected_cash`, `counted_cash`.
* `cash_operations`: внесення / вилучення готівки протягом зміни.
* Фіскалізація (ПРРО) — через інтерфейс `FiscalProvider`; на старті реалізація-заглушка, що зберігає чек локально.

### 4.10. Сповіщення
* Інтерфейс каналу (`NotificationChannel`) + шаблони повідомлень (конкретний канал — ADR-5).
* Тригери (через outbox-події): замовлення підтверджено, готове до видачі, передано кур'єру, резерв самовивозу скоро спливе.

### 4.11. Що взято зі Spree Commerce, а що ні
**Взято:**

| Елемент Spree | Де у нас |
|---|---|
| `products` / `variants` з майстер-варіантом, окрема таблиця `prices` | 4.2 |
| `taxonomies` — кілька незалежних дерев категорій | 4.2 |
| `stock_locations`, `stock_items`, `stock_movements`, `stock_transfers` | 4.3 |
| Документ-джерело руху товару (`originator`) | 4.3, але через `source_type` / `source_id` з перевіркою |
| Три незалежні стани замовлення: `state`, `payment_state`, `shipment_state` | 4.5 |
| `state_changes` — історія переходів станів | 4.1, 4.5 |
| Людиночитні `number` документів, `token` для гостя | 4.1, 4.5 |
| Денормалізовані підсумки в `orders` + єдиний updater | 4.5 |
| Знімок ціни й собівартості в рядку замовлення (`line_items.price`, `cost_price`) | 4.5 |
| `adjustments` з прив'язкою до замовлення / рядка / відвантаження та джерелом | 4.5 |
| `promotions` / `promotion_rules` / `promotion_actions` / коди | 4.5 |
| `shipments` з точкою відвантаження, `shipping_rates` з обраним варіантом | 4.7 |
| `payments`, `refunds`, журнал відповідей провайдера | 4.6 |
| Повернення: `return_authorizations` → `return_items` → `refunds` + довідники причин | 4.5 |
| `deleted_at` (м'яке видалення), `public_metadata` / `private_metadata` | 4.1 |

**Не взято:**

| Елемент Spree | Чому |
|---|---|
| Кошик як замовлення (`state = cart`) і кроки checkout `address → delivery → payment → confirm` у БД | Кошик — окремий модуль (ADR-9) |
| Зони доставки за країнами / регіонами (`zones`, `zone_members`) | Доставка в межах міста — радіус або полігон (ADR-8) |
| Polymorphic-зв'язки без FK | Цілісність має гарантуватись — див. 4.1 |
| `inventory_units` (окремий запис на кожну одиницю товару) | Для штучних квітів зайве; задачу покривають `stock_reservations` |
| Списання залишку лише при завершенні замовлення, без резерву | Потрібен резерв під час оформлення (4.5) |
| Nested Sets (`lft` / `rgt`) для дерева категорій | `ltree` простіший у PostgreSQL (4.2) |

**Чого в Spree немає (власна частина):** резервування при оформленні, партії з FIFO, комплекти-букети (у Spree лише окремим розширенням), інвентаризація, POS і касові зміни, слоти доставки, отримувач і листівка.

## 5. Архітектура аналітики та дашбордів (Без навантаження на основну БД)
Для адмін-панелі власника мережі заборонено виконувати важкі агрегуючі запити (`SUM`, `COUNT`, `GROUP BY`) по живих таблицях `orders` та `stock_movements`. Використовуються два механізми:

1. **PostgreSQL Materialized Views:**
   * Для звітів по продажах, популярності квітів, маржі та статистиці списань (у штуках і гривнях) по кожному магазину створюються матеріалізовані представлення (наприклад, `mv_daily_location_sales`, `mv_waste_analytics`).
   * Оновлюються у фоні через Cron-воркер NestJS (`REFRESH MATERIALIZED VIEW CONCURRENTLY`) раз на 10–15 хвилин без блокування читання.
   * Належать модулю `analytics` (задокументований виняток з правила ізоляції, див. 2.2).
2. **Агрегаційні таблиці реального часу (Rollup Tables):**
   * Легка таблиця `realtime_location_metrics` (`date`, `location_id`, `orders_count`, `revenue`, `pos_sales_count`, `online_sales_count`).
   * Оновлюється атомарним інкрементом (`UPDATE ... SET revenue = revenue + X`) споживачем outbox-події `OrderCompleted`.
   * Інкремент і запис у `processed_events` виконуються в одній транзакції — повторна доставка події не подвоює виручку.

## 8. Інструкції для локального AI-асистента
При генерації коду, схем БД та архітектурних рішень у цьому проєкті дотримуйся таких правил:
1. Завжди проєктуй схеми БД з урахуванням **мульти-локаційності** (`location_id`) та роботи на рівні **варіацій** (`variant_id`).
2. Дотримуйся принципу **модульного моноліту в NestJS**: розділяй бізнес-логіку на чіткі модулі (див. розділ 6), використовуй DTO, сувору типізацію TypeScript. Міжмодульні події — **лише через Transactional Outbox**, обробники подій — ідемпотентні.
3. Будь-які операції зі зміною залишків товару (`location_stocks`) обгортай у **транзакції БД** із захистом від race conditions (одночасний продаж на касі та на сайті) та обов'язковим записом у журнал `stock_movements` (і в `stock_batches`, де це застосовно).
4. На фронтенді (**TanStack Start**) використовуй URL search-параметри як єдине джерело істини для фільтрів каталогу, пагінації та вибору поточного магазину користувача.
5. Гроші — `bigint` у копійках; час — `timestamptz` в UTC, бізнес-логіка днів і слотів — у Europe/Kyiv.
6. Зовнішні інтеграції (оплата, фіскалізація, сповіщення) — завжди через інтерфейс-адаптер, щоб провайдера можна було замінити.
7. Кожен webhook і кожен POST, що створює гроші / рух товару, приймає ключ ідемпотентності.
8. Стани замовлень, оплат, відвантажень і повернень змінюються лише через сервіс машини станів із записом у `state_changes`; підсумки замовлення — лише через `OrderUpdater`; суми — лише через `PriceCalculator`.
9. Кошик не є замовленням: не додавай стан `cart` до `orders` і не звертайся до сховища кошика в обхід `CartRepository`.
10. NestJS 12 — ESM-only: відносні імпорти в `apps/api` закінчуються на `.js`, `__dirname` немає (`import.meta.dirname`), моки в тестах — `vi.fn()` (Vitest).
11. Спільний код — лише в `packages/*` з явним полем `exports`; імпорт тільки того, що пакет експортує, без глибоких шляхів у чужий пакет.
12. БД (Drizzle): таблиці модуля — у `src/<module>/<module>.schema.ts`, реєстрація — у `src/database/schema.ts`; доступ — через `@Inject(DATABASE)`. Міграції лише генеруються drizzle-kit (або `--custom` для розширень / views); застосовану міграцію не редагувати — додавати нову. Міграції запускаються окремою командою, не при старті застосунку.
13. Конфігурація: кожна змінна середовища оголошується в zod-схемі застосунку (`apps/api/src/config/env.schema.ts`, `apps/web/src/env.server.ts`) і перевіряється при старті — у production застосунок не запускається без обов'язкових значень. Код читає змінні лише через `AppConfigService` (api) або `getServerEnv()` (web); прямий `process.env` поза файлами конфігурації заборонений (oxlint `node/no-process-env`). Нову змінну також додавати в `turbo.json` → `passThroughEnv` і `docs/modules/platform/configuration.md`.
14. Події між модулями — лише через outbox: `outbox.add(tx, { topic, key, payload })` всередині `db.transaction()` тієї самої бізнес-зміни (ніколи `event-emitter` чи прямий виклик іншого модуля); обробник — `@OnOutboxMessage(topic, { consumer })` зі стабільною назвою `consumer`, ідемпотентний; зміни в БД з обробника — через `ctx.processInTransaction(tx, …)`.
15. Документація — у `docs/` (правила в `docs/README.md`), оновлюється в тому ж PR, що й код: змінилась поведінка — оновити reference модуля; з'явився екран для персоналу — додати guide для кожної ролі з її `audience`; розв'язано неочевидну проблему — запис у `journal.md` модуля (симптом, причина, виправлення, урок). Перед роботою над модулем прочитати його `docs/modules/<module>/` і journal. Секретів і персональних даних у `docs/` немає: репозиторій публічний.

## 9. Архітектурні рішення (ADR)

### 9.1. Прийняті рішення

#### ADR-1: ORM — Drizzle
**Статус:** прийнято, 2026-11-15.

**Контекст.** Порівнювались Drizzle та Prisma за вимогами цього документа.

| Вимога | Drizzle | Prisma |
|---|---|---|
| `SELECT ... FOR UPDATE` при резервуванні (4.5) | ✅ у конструкторі запитів (`.for('update')`, `skipLocked`), типізовано | ❌ лише сирий SQL (`$queryRaw` / TypedSQL) |
| Materialized Views + `REFRESH ... CONCURRENTLY` (розділ 5) | ✅ `pgMaterializedView`, `db.refreshMaterializedView(v).concurrently()` | ⚠️ views — preview, оновлення сирим SQL |
| `ltree` для категорій (4.2) | ✅ `customType` | ❌ `Unsupported("ltree")`, без типізації |
| Ізоляція модулів (2.2) | ✅ схема — TS-код, модуль експортує лише свої таблиці | ❌ один спільний клієнт з усіма моделями |
| Outbox в одній транзакції (2.4) | ✅ `db.transaction()` з рівнем ізоляції | ✅ інтерактивні транзакції |
| Міграції для рев'ю | ✅ SQL-файли drizzle-kit | ✅ SQL-файли Prisma Migrate |
| Монорепо | ✅ без кодогенерації | ⚠️ окремий крок `prisma generate` |

**Рішення.**
1. Drizzle ORM + drizzle-kit, драйвер PostgreSQL.
2. Версія: стабільна гілка `0.45.x`; перехід на `1.0` — після стабільного релізу (на 2026-11-15 він у стадії RC).
3. Кожен модуль оголошує свої таблиці у власній схемі Drizzle і не імпортує таблиці інших модулів.
4. Підключення до NestJS — власний `DatabaseModule` (провайдер з інстансом `db`); офіційний `@nestjs/drizzle` (на 2026-11-15 — `0.0.2`) переглянути, коли стабілізується.

**Наслідки.** Менше зручностей «з коробки», ніж у Prisma (студія, DSL-схема), але критичні запити (резерв з блокуванням, `ltree`, materialized views) пишуться типізовано без сирого SQL.

#### ADR-11: RustFS замість MinIO для локального S3
**Статус:** прийнято, 2026-11-15.

**Контекст.** MinIO припинив публікацію готових образів community-версії: на 2026-11-15 образу `minio/minio` на Docker Hub немає, а `quay.io/minio/minio` вимагає автентифікації.

**Рішення.** Для локальної розробки — `rustfs/rustfs` (Apache 2.0, S3-сумісний, ті самі порти 9000 / 9001). Бакет створює одноразовий сервіс `s3-init` на `amazon/aws-cli`. Застосунок звертається до сховища лише через стандартний S3 API (endpoint, ключі, бакет з конфігурації), тож провайдер у продакшені обирається окремо (ADR-7) без змін коду.

#### ADR-12: Transactional outbox — офіційний `@nestjs/outbox`
**Статус:** прийнято, 2026-11-15.

**Контекст.** Початковий план (2.4) — власні таблиці `outbox_events` / `processed_events` і relay на BullMQ. Команда NestJS випустила `@nestjs/outbox` зі сховищем PostgreSQL, яке пише через Drizzle (`fromDrizzle(db)`).

**Рішення.**
1. `@nestjs/outbox` (точна версія, на 2026-11-15 — `0.1.4`) з `PostgresOutboxStore` у схемі `nest_outbox`.
2. Повідомлення додаються лише в транзакції (`outbox.add(tx, …)`; без транзакції — `OutboxTransactionRequiredError`). Обробники — `@OnOutboxMessage(topic, { consumer })`; запис у ту саму БД — через `ctx.processInTransaction()`.
3. Розробка: один процес (API теж запускає relay). Production: API з `OUTBOX_RELAY=off` + один чи кілька процесів `worker`.
4. Схема outbox: у розробці створюється при старті; у production — `pnpm db:migrate` (застосунок з застарілою схемою не стартує).
5. Inbox-записи старші за 30 днів видаляє щоденна задача (`OutboxRetention`).
6. BullMQ не є outbox: його `Queue.add()` не може приєднатися до нашої транзакції. BullMQ лишається для відкладених задач.

**Чому не власна реалізація.** Пакет уже має оренду з fencing-токенами (кілька relay не доставляють одне повідомлення), порядок за ключем, повтори з backoff, dead-letter, inbox, graceful shutdown і події для моніторингу — власна реалізація повторила б це з більшою кількістю помилок.

**Ризик.** Версія `0.x`: фіксуємо точну версію, а контрактні тести пакета (`outboxStoreContract`, `outboxInboxStoreContract` з `concurrent: true`) запускаються проти нашого PostgreSQL у `test:e2e`.

#### ADR-9: Кошик — окремий модуль зі сховищем у PostgreSQL (не замовлення, як у Spree)
**Статус:** прийнято, 2026-11-15.

**Контекст.** У Spree кошик — це рядок `orders` зі `state = cart`. Початкова версія цього документа зберігала кошик у Redis з TTL. Потрібно було вирішити два незалежні питання: (1) кошик — це замовлення чи окрема сутність; (2) де зберігати кошик.

**Питання 1 — кошик окремо від замовлення:**

| | Кошик = замовлення (Spree) | Кошик окремо |
|---|---|---|
| Повторне використання розрахунку цін | ✅ один код | ⚠️ потрібен спільний `PriceCalculator` |
| Чистота `orders` | ❌ кинуті кошики (більшість) лишаються в `orders`, потрібна чистка й фільтр у кожному запиті | ✅ лише реальні замовлення |
| Кошики ботів і краулерів | ❌ у фінансовій таблиці | ✅ ізольовані |
| Межі модулів | ❌ один модуль і таблиця | ✅ `cart` і `orders` окремо |

**Питання 2 — сховище:**

| | Redis | PostgreSQL |
|---|---|---|
| Навантаження на основну БД | ✅ немає | ⚠️ запис на кожну дію з кошиком |
| Прибирання | ✅ TTL | ⚠️ фоновий воркер |
| Надійність | ❌ втрата при рестарті / витісненні без AOF і `noeviction` | ✅ |
| Аналітика кинутих кошиків, нагадування | ❌ дані зникають після TTL | ✅ звичайний SQL |
| Оформлення | ⚠️ два сховища | ✅ одна транзакція: кошик → замовлення → резерв |

**Рішення.**
1. Кошик — окремий модуль `cart`, не стан замовлення.
2. Сховище на старті — PostgreSQL (`carts`, `cart_items`) за інтерфейсом `CartRepository`.
3. Розрахунок сум винесено в модуль `pricing` (`PriceCalculator`), який використовують і `cart`, і `orders`.
4. Реалізація на Redis підставляється лише якщо навантажувальні тести k6 (PLT-09) покажуть потребу.

**Наслідки.** Аргумент «stateless» не стосується вибору між Redis і PostgreSQL: сервер застосунку не тримає стану в обох випадках. Навантаження від кошиків мережі з 5–9 точок (включно з піками 14 лютого та 8 березня) PostgreSQL витримує; Redis для кошика стає доцільним на масштабі великого маркетплейсу.

#### ADR-10: Монорепозиторій на pnpm workspaces + Turborepo
**Статус:** прийнято, 2026-11-15.

**Контекст.** Потрібен один репозиторій для бекенду, фронтенду та спільного коду, в якому зміна одного застосунку не перезбирає й не перевикладає інші. Розглядались Turborepo та Nx.

| | Turborepo | Nx |
|---|---|---|
| Поріг входу | Низький: `turbo.json` поверх звичайних `package.json` | Вищий: генератори, executors, плагіни |
| Збірка лише зміненого (`--affected`) | Є | Є |
| Граф залежностей | `turbo run build --graph` (файл) | `nx graph` (інтерактивний UI) |
| Межі модулів | Поле `exports` кожного пакета + лінтер | Вбудоване правило `@nx/enforce-module-boundaries` |
| Підтримка NestJS | Звичайний `nest build` у застосунку | Офіційний плагін `@nx/nest` |

**Рішення.**
1. pnpm 12 workspaces + Turborepo 2.
2. `apps/*` — застосунки, кожен збирається й деплоїться окремо: `api` (NestJS), `web` (TanStack Start). Фоновий процес `worker` — друга точка входу `apps/api` (`src/worker.ts`) на тих самих модулях, без HTTP (PLT-04); окремий пакет потрібен лише тоді, коли worker отримає код, якого немає в API.
3. `packages/*` — спільний код. Бізнес-модулі виносяться в пакети, коли їх починають використовувати два застосунки; межі модуля задаються полем `exports`.
4. Незалежний деплой: CI збирає лише змінене (`turbo run build --affected`), Docker-образ застосунку будується з `turbo prune <app> --docker` (PLT-07, PLT-10).

**Наслідки.** Винесення модуля в окремий сервіс = новий застосунок в `apps/`, що імпортує той самий пакет модуля. Перехід на Nx можливий без зміни структури `apps/` + `packages/`, якщо застосунків стане більше 10 або знадобиться розподілене кешування.
